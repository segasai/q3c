# Q3C 3.0 redesign proposal

Status: design document, no code yet.
Scope decisions taken: PostgreSQL floor **14+** for 3.0 (2.0.x maintained for older
servers); **clean break** to the true spherical (focal) ellipse predicate.

Goals, in the author's terms:

1. Row estimates for q3c queries must come from table statistics, not a hardcoded
   uniform-sky constant, so they stop being "often very wrong".
2. Plans must stop flipping on small parameter changes (a consequence of 1, plus
   honest costing of the index path).
3. The hard geometric limits — 35° radius/major-axis cap, ~23° polygon diameter,
   100-vertex polygon cap, fixed 50+50 range arrays — must go away.

Hard constraints:

- The top-level API is preserved: `q3c_radial_query`, `q3c_join`, `q3c_ellipse_query`,
  `q3c_ellipse_join`, `q3c_poly_query`, `q3c_join_pm` keep their names and signatures
  and remain boolean predicates usable in `WHERE`.
- The indexing mechanism stays a plain btree on the expression `q3c_ang2ipix(ra,dec)`.
  Existing user indexes must keep working with **zero action** on upgrade.

The one-paragraph summary: replace the two hacks the current design is built on —
machine-generated SQL bodies that PostgreSQL inlines into fixed 100-way OR chains, and
the dummy `==<<>>==` operator that smuggles in a constant selectivity — with **planner
support functions** (PG 12+), and replace the conic-on-cube-face geometry with a **3D
unit-vector engine** that classifies quadtree cells against regions exactly, at any
size, emitting an adaptive number of ipix ranges. The public functions become plain C
predicates (the exact test) whose support function rewrites them at plan time into
index-matchable range clauses with honest, statistics-based selectivity.

## 1. Diagnosis: why the current design misestimates and caps out

### 1.1 How a q3c query works today

The public functions are `LANGUAGE SQL` bodies that PostgreSQL inlines. For
`q3c_radial_query` the body (generated by `utils/generate_rad_query.pl`) is a
disjunction of exactly 50 "full" + 50 "partial" range conditions:

```
(q3c_ang2ipix($1,$2) >= q3c_radial_query_it($3,$4,$5,0,1) AND
 q3c_ang2ipix($1,$2) <  q3c_radial_query_it($3,$4,$5,1,1)) OR
... (100 ranges, 200 *_it calls) ...
AND q3c_sindist($1,$2,$3,$4) < POW(SIN(RADIANS($5)/2),2)
```

For constant center/radius the `*_it` calls const-fold, so the executor sees 100
`BETWEEN` conditions on the expression index — of which typically **~96 are the empty
padding range `[1,-1]`** emitted by `array_filler()` (q3cube.c:2296) because the SQL
demands fixed-length arrays. `q3c_join` uses the same trick with 4 ranges from
`q3c_get_nearby` plus the selectivity operator (see below). The `*_it` functions cache
the computed range arrays in process-`static` buffers keyed on the query parameters
(q3c.c:752-824), which is why the `*_query` family has never been marked
`PARALLEL SAFE`.

### 1.2 Where the row estimates actually go wrong

Dissecting the estimate for each query class:

- **`q3c_radial_query` (constant center).** There is no custom selectivity at all. The
  planner estimates each folded range from the expression-index histogram — and the 96
  padding ranges each collapse to ~1e-10, so the OR estimate itself is usually *not*
  the main error. The dominant errors are (a) the trailing
  `q3c_sindist(...) < const` clause: a function-call inequality with no statistics
  contributes the default selectivity **0.3333**, flattening every estimate by 3x; and
  (b) histogram resolution — with `default_statistics_target = 100` each bucket holds
  1% of the table, and within-bucket linear interpolation in ipix space is a poor model
  of clustered sky data at survey-typical radii.
- **`q3c_join`.** The range bounds are `q3c_nearby_it(a.ra,...)` FuncExprs — not
  Consts — so `scalarineqsel` bails to `DEFAULT_RANGE_INEQ_SEL = 0.005` per arm; the
  4-arm OR gives ≈0.0199; times 0.3333 for the sindist clause; times the dummy
  operator's `3.14·r²/41252` (q3c.c:140). The product is a systematic ~150x
  *underestimate* stacked on the geometric cone fraction — itself wrong whenever the
  sky coverage is not uniform (which is every real catalogue).
- **Cost side.** The 96 dead ranges are each planned as a Bitmap Index Scan, inflating
  the index path's cost ~25x. Bad rows + bad cost = the plan flips between bitmap scan,
  seq scan, and merge join on tiny parameter changes; hence the README's advice to
  `set enable_seqscan = off` etc.

Latent bugs in the current estimator, verified in the tree:

- `pgq3c_sel` / `pgq3c_seljoin` cast the result of `estimate_expression_value()` to
  `Const` **without an `IsA` check** (q3c.c:129, q3c.c:175). A radius that does not
  fold to a Const — e.g. the README-documented `q3c_join(a.ra, a.dec, b.ra, b.dec,
  a.err)` — makes the planner read garbage (`Var` fields reinterpreted as a Datum).
- `q3c_join_pm` passes the **wrong argument** to the selectivity operator:
  `$10` (max_epoch_delta, years) instead of `$11` (radius, degrees)
  (scripts/q3c--2.0.5.sql:258). A 30-year epoch span estimates as if it were a
  30-degree search radius.
- The two estimator bodies are duplicated verbatim; the estimate uses flat-disc
  `πr²` rather than the spherical cap `2π(1−cos r)` (immaterial at small radii, wrong
  at large ones).

### 1.3 Where the geometric limits come from

The region→ranges engine projects the query region onto each touched cube face as a
**second-order curve** (conic) and classifies quadtree squares by evaluating that conic
at the corners (`q3c_circle_cover_check`, q3cube.c:1963). This is exact only while the
projection is an ellipse. Consequences:

- `Q3C_MAXRAD = 35°` (common.h:186): above it the cone's projection can become a
  parabola/hyperbola on a main face, so the code silently degrades to a **whole-sky
  partial range** (q3cube.c:2358-2379) — correct but a full scan.
- `Q3C_MINDISCR = 1e-10`: just *below* 35°, near-degenerate conics make the code take
  **entire faces** as partial ranges; this regime produced the out-of-bounds/missed-rows
  bugs fixed in issue #49 (commit 592846a).
- Polygons are gnomonically projected; any vertex crossing the face horizon is a hard
  error ("diameter >~23 degrees unsupported", q3c.c:1150; the README says 25 — they
  disagree). The main face is chosen from vertex 0 only; `Q3C_MAX_N_POLY_VERTEX = 100`.
- Output is two fixed 50-pair arrays (`Q3C_NFULLS`/`Q3C_NPARTIALS`), duplicated in
  three places (common.h, the Perl generator, every generated SQL body). Refinement
  depth is fixed at `Q3C_MAX_DEPTH = 4`; overflow is
  `elog(ERROR, "...too many ipix ranges. This is a bug...")`. Ranges are emitted
  unsorted and uncoalesced, and the full/partial distinction is computed but never
  exploited — the shipped SQL applies the exact recheck to everything.
- Work stacks are two fixed 11000-entry arrays **on the C stack** (~528 KB per call,
  q3cube.c:2341) with no bounds checking in `q3c_stack_expand`.

## 2. Verified PostgreSQL mechanics the redesign rests on

All of these exist since PG 12 and are therefore safe under the PG 14 floor. Each was
checked against the PostgreSQL sources; file references are to the PG tree.

1. **Planner support functions**: `CREATE FUNCTION ... SUPPORT fn`
   (`pg_proc.prosupport`, `src/include/nodes/supportnodes.h`) with request types
   `SupportRequestSimplify`, `SupportRequestSelectivity`, `SupportRequestCost`,
   `SupportRequestRows`, `SupportRequestIndexCondition`. Attaching SUPPORT requires
   superuser — fine for an untrusted C extension.
2. **Simplify runs before inlining.** In `simplify_function()`
   (`optimizer/util/clauses.c`, from `eval_const_expressions_mutator`) the order is:
   prosupport Simplify → `evaluate_function()` (const-folding) → `inline_function()`.
   So a support function sees the call before any SQL-body inlining would.
3. **Parallel safety is decided on the raw parse tree.** `standard_planner()` computes
   `max_parallel_hazard()` *before* simplification, so the public function's own
   `proparallel` marking gates parallel plans regardless of what it simplifies into.
   Today's unmarked (⇒ UNSAFE) `q3c_radial_query` disables parallelism for every cone
   search; a stateless C body marked PARALLEL SAFE unlocks parallel bitmap heap scans.
4. **Boolean function clauses route to support selectivity.** `clause_selectivity_ext`
   → `function_selectivity()` (`optimizer/util/plancat.c`) consults
   `SupportRequestSelectivity` for **both restriction and join** contexts (join:
   `varRelid == 0`, `sjinfo != NULL`). Without a handler the default is 0.3333333.
5. **Index-condition generation.** `match_funcclause_to_indexcol()`
   (`optimizer/path/indxpath.c`) fires when a qual is a `FuncExpr` whose function has
   prosupport **and one of whose direct arguments matches the index column expression**
   via `equal()` (which compares funcid, funcformat, collations, and argument trees).
   The support function returns an **implicitly ANDed** list of indexable clauses — it
   can never return an OR. This single fact shapes the join design (§4.3).
   Precedent: PostGIS ≥ 3.0's `postgis_index_supportfn` (`ST_DWithin(a,b,r)` →
   `a && expand(b,r)`).

## 3. New geometry engine

### 3.1 Cells as spherical quadrilaterals — exact 3D classification

The key geometric fact (verified from `q3c_ang2ipix_xy`, q3cube.c:120-214): a cube-face
grid line is the intersection of the face plane with a plane through the origin, so its
projection on the sphere is a **great-circle arc**. Every quadtree cell is therefore a
spherical quadrilateral bounded by four great-circle arcs and can be classified against
a query region exactly in 3D, with no per-face projection of the *region* at all.

Per-face orthonormal frames (outward axis `a`, in-face directions `e1`, `e2`), derived
from the existing projections and to be pinned down by round-trip tests:

| face | a | e1 | e2 |
|------|---|----|----|
| 0 (N) | (0,0,1) | (0,1,0) | (−1,0,0) |
| k = 1..4 | (cos θ, sin θ, 0), θ = 90°(k−1) | (−sin θ, cos θ, 0) | (0,0,1) |
| 5 (S) | (0,0,−1) | (0,1,0) | (1,0,0) |

Cell primitives (new file `q3c_vec.c`):

- Corner of a level-L cell at integer grid coords (X,Y): face coordinates
  `x = 2X/2^L − 1`, `y = 2Y/2^L − 1` are dyadic rationals, **exact in double**, so
  neighbouring cells get bit-identical shared corner vectors — neighbour
  classifications can never disagree on a shared boundary. Corner unit vector:
  `normalize(a + x·e1 + y·e2)` (one sqrt).
- Edge great-circle normals: line `x = x0` has normal `∝ e1 − x0·a`; `y = y0` has
  `∝ e2 − y0·a`. No cross products.
- Cell ↔ ipix: a level-L cell is exactly the half-open range
  `[face·nside² + morton(X,Y)·4^(30−L), +4^(30−L))` via the existing
  `q3c_xiyi2ipix`. Contiguous by construction, which makes range emission and
  coalescing trivial.
- Each cell caches its 4 corners, its center vector `v0`, and circumradius
  `θ_cell = max angle(v0, corner_i)` computed with `atan2(|v0×u|, v0·u)` (robust at 0
  and π, unlike acos).

### 3.2 Cap (circle) classification — any radius 0…180°

Cap: center `c`, radius `r`, interior `{v : v·c ≥ cos r}`.

**Tier 1** (one dot product + one atan2), valid for any `r` by the spherical triangle
inequality: with `θ0 = angle(v0, c)` —
`θ0 ≥ r + θ_cell + ε` ⇒ DISJUNCT; `θ0 ≤ r − θ_cell − ε` ⇒ COVER. This resolves every
cell not within one cell-diameter of the boundary circle.

**Tier 2** (boundary cells only):

1. Count corners inside (`u_i·c ≥ cos r`; within `ε` of the boundary ⇒ PARTIAL).
2. Mixed corners ⇒ PARTIAL (certain).
3. All 4 inside ⇒ COVER iff no edge crosses the boundary circle **and** `−c` is not in
   the cell (handles `r > 90°`, where the cap's complement is a small cap around `−c`);
   else PARTIAL.
4. All 4 outside ⇒ DISJUNCT iff no edge crosses the boundary **and** `c` is not in the
   cell; else PARTIAL.

Edge-arc vs boundary-circle intersection is closed-form (one sqrt): for edge normal
`n`, `d = c·n`, `ρ² = 1 − d²`; if `cos²r > ρ²` the great circle misses the boundary
circle; otherwise the two candidate points are
`p± = (cos r/ρ²)(c − d·n) ± (√(ρ² − cos²r)/ρ²)(n × c)`, each accepted iff within the
arc (two sign tests). Near-tangency within ε ⇒ PARTIAL.

This kills `Q3C_MAXRAD`, `Q3C_MINDISCR`, and the issue-#49 bug class outright: there is
no parameter regime where the test changes character. Degenerate cases need no special
code paths: a cap containing whole faces yields COVER at the face roots (one coalesced
range for 3+ faces); `r ≥ 180°` yields the single range `[0, 6·nside²)`; `r = 0` or
sub-pixel caps resolve to the 1–4 containing pixels via the `c`-in-cell clause;
poles/wraparound/face corners don't exist as concepts once everything is unit vectors.

### 3.3 The conservative-direction contract

With `M` the exact recheck predicate (`q3c_sindist < …` etc.), the engine guarantees:

1. **DISJUNCT ⇒ no point of the closed cell satisfies M** (tested against the
   ε-*enlarged* region). A truly disjoint cell may be labelled PARTIAL — performance
   loss only.
2. **COVER ⇒ every point of the cell satisfies M** (tested against the ε-*shrunk*
   region), asserted only when the output's `cover_certain` flag is set.
3. PARTIAL carries no guarantee.

Invariants consumed by the planner layer: `fulls ∪ partials ⊇ region` always;
`fulls ⊆ region` when `cover_certain`. This is what finally lets the query shape become

```
(ipix IN full-ranges) OR (ipix IN partial-ranges AND exact_recheck)
```

so fully-covered ranges **skip the recheck** — a win the current code computes but
never uses. ε is a single angular tolerance (~1e-11 rad, ≈1% of a depth-30 pixel),
calibrated empirically by fuzzing engine classifications against the recheck's
haversine arithmetic (§7).

### 3.4 Ellipse — clean break to the focal definition

The current `q3c_in_ellipse` is an opaque Maple-generated projected form from which no
exact cell test can be derived. 3.0 redefines the ellipse as the true spherical ellipse:

```
E = { v : d(v,F1) + d(v,F2) ≤ 2a },   F± = rotate(c, ±f along PA),  cos f = cos a / cos b
```

- The recheck becomes two atan2-based angular distances; **engine and recheck share one
  predicate** (single source of truth).
- The margin `s(v) = d(v,F1) + d(v,F2) − 2a` is 2-Lipschitz in angular distance, giving
  certain cell tests: `s(v0) > 2θ_cell + ε` ⇒ DISJUNCT;
  `s(v0) < −2θ_cell − ε` ⇒ COVER; else corner tests / PARTIAL. DISJUNCT is *local*, so
  over-coverage of elongated ellipses converges linearly with depth.
- Input validation: `0 < axis_ratio ≤ 1` becomes an error check (today `ratio > 1`
  silently yields NaN eccentricity, q3c.c:837); semi-major axis allowed to <90°
  initially (2.5x the old cap), extensible later.
- PA convention at the poles gets an explicit documented tangent frame
  (east = normalize(ẑ×c), north = c×east).
- Deletes ~450 lines of Maple-generated polar/equatorial variants
  (q3cube.c:1508-1961). Membership changes slightly near the boundary of large or
  elongated ellipses relative to 2.x — accepted as part of the major version.

### 3.5 Polygon — spherical, unlimited size and vertex count

- Vertices as unit vectors, dynamic (palloc'd) arrays — `Q3C_MAX_N_POLY_VERTEX` dies.
  Edges are great-circle **minor arcs**; consecutive equal/antipodal vertices are
  errors.
- Membership semantics, documented: odd crossing parity of the arc from the test point
  to a defined exterior reference point `v_ref` = the antipode of the polygon's
  bounding-cap center (deterministically perturbed if the boundary passes within ε).
  This reproduces current behaviour for every polygon the old code accepted (all were
  <23° across), gives well-defined odd-even semantics for self-intersecting polygons,
  and supports any diameter. Caveat (documented): the component containing `v_ref` is
  "outside", so a region larger than the hemisphere around its own vertices must be
  expressed as a complement.
- Cell classification: bounding-cap prefilter; then any vertex inside cell ⇒ PARTIAL;
  any polygon-edge/cell-edge arc intersection (candidates `±normalize(m_i × n_j)`,
  four in-arc sign tests each, ε toward "intersects") ⇒ PARTIAL; else classify the
  whole cell by one parity test of a corner ⇒ COVER or DISJUNCT, both certain.
- Removes: the ~23° hard error, the gnomonic horizon problem, the vertex-0 main-face
  fragility, and the README/code disagreement about the limit.

### 3.6 Adaptive refinement with a range budget

Replace the fixed-depth walk and fixed 50+50 arrays with greedy priority-queue
refinement:

```
seed the 6 face-root cells
loop:
    T = largest pending PARTIAL cell (max-heap by area)
    stop if ranges_emitted + heap_size + 3 > max_ranges     (budget)
         or T.level ≥ max_level (≤30)
         or T.diameter ≤ resolution_floor                    (join mode)
         or overcoverage ≤ max_overcov · region_area         (quality met)
    split T; classify children: COVER → fulls, PARTIAL → heap, DISJUNCT → drop
drain heap into partials; sort; coalesce adjacent ranges
```

- **Budget-exact**: each split removes one pending range and adds ≤4, so the final
  count never exceeds `max_ranges`. Overflow degrades to *coarser coverage*, never to
  an error — the "too many ipix ranges, this is a bug" class becomes structurally
  impossible.
- Splitting the largest partial first maximizes over-coverage reduction per range
  spent — exactly what row estimation wants.
- Output: `q3c_rangelist { q3c_range *full; int nfull; q3c_range *part; int npart;
  bool cover_certain; }`, sorted and coalesced (cells partition the quadtree, so
  sorted ranges are disjoint; coalescing works across face boundaries). Today's
  unsorted/uncoalesced output typically shrinks 20–40% for identical coverage.
- Options struct: `{ int max_ranges; int max_level; double max_overcov;
  double resolution_floor; }`. Defaults: **plan-time constant queries**
  `max_ranges = 256, max_overcov = 2%` (a range costs one btree descent in a
  BitmapOr; over-coverage costs heap fetches); **per-outer-row joins**
  `max_ranges = 12, resolution_floor = diameter/2`, reproducing today's
  4-corner-cell `q3c_get_nearby` granularity but correct across faces and poles.
  Exposed as a GUC (`q3c.plan_budget`) and/or optional function argument.
- N(radius) must vary smoothly (no discrete jumps that lurch the bitmap cost) — a
  plan-stability requirement, not just aesthetics.

### 3.7 Reentrancy and memory

- **No statics anywhere in the engine.** All state in a caller-provided growable
  context; allocation through a `q3c_alloc` seam (palloc in PG with explicit
  MemoryContext, malloc in the standalone build). `ctx` reuse makes per-outer-row join
  calls allocation-free after warm-up.
- C-stack usage O(1); the two 11000-entry stack arrays (~528 KB per call) disappear.
- Everything becomes PARALLEL SAFE. Error handling returns codes in the engine; only
  the PG wrapper `ereport`s.
- Engine API to the planner layer:
  `q3c_region_prepare(...)` (validate + precompute, once per query) →
  `q3c_region_set_center(desc, ra, dec)` (cheap per-row update for joins; shape and
  radius fixed) → `q3c_cover(hprm, desc, opts, ctx, &rangelist)`. Plus
  `q3c_ranges_solid_angle(rangelist)` for the selectivity layer (§4.4).

### 3.8 What survives untouched

`q3c_ang2ipix` / `q3c_ang2ipix_xy` / `q3c_ipix2ang` / `q3c_xiyi2ipix`, the Morton
lookup tables, the ipix layout `face·nside² + morton(xi,yi)`, `q3c_dist`,
`q3c_sindist`, `q3c_pixarea` — i.e. everything an existing index depends on.

File map: new `q3c_vec.c` (frames, cell primitives, arc intersections),
`q3c_region.c` (region descriptors + the membership predicates shared by engine and
rechecks), `q3c_cover.c` (classification + refinement + output). `q3cube.c` shrinks
from ~2900 to ~1100 lines (all conic/bbox/stack machinery deleted); the gnomonic
machinery in `q3c_poly.c` is replaced by the spherical parity predicate; the Perl SQL
generator is deleted.

## 4. Planner integration

### 4.1 Public predicates become C functions with SUPPORT

All seven public predicates are re-created (`CREATE OR REPLACE`, identical signatures)
as `LANGUAGE C, IMMUTABLE, PARALLEL SAFE, SUPPORT q3c_support`. Their C bodies are the
**exact geometric test only** — `q3c_sindist`-based for circles, the focal predicate
for ellipses, the parity test for polygons — stateless, capless, correct under any
plan. That body is the honest fallback whenever the support function declines to
rewrite (center depends on the same row, volatile arguments, etc.).

Why not keep SQL bodies plus SUPPORT (the ordering in §2.2 would allow it): (a) the
parallel-hazard check reads the *function's own* marking before simplification, and the
SQL bodies call the statically-caching `*_it` functions, so marking them PARALLEL SAFE
would be a lie; (b) when Simplify declines, the inlined body still executes with all
the old caps and cache behaviour; (c) EXPLAIN stops showing 100-clause zombie
expansions.

### 4.2 Constant-center path (`SupportRequestSimplify`)

For `q3c_radial_query(t.ra, t.dec, Const, Const, Const)` the support function calls the
engine (budget ≈256) and returns a replacement tree:

```
(   (q3c_ang2ipix(ra,dec) >= Const lo_1 AND q3c_ang2ipix(ra,dec) < Const hi_1)
 OR ...one arm per REAL range, no padding...
) AND q3c_dist_ok(Const cra, Const cdec, ra, dec, Const rad)
```

Construction details that make it work:

- The coordinate argument nodes are **copied verbatim** from the original call
  (`copyObject`), reproducing exactly what SQL inlining produced before — anything that
  matched the expression index in 2.x matches in 3.0.
- The `q3c_ang2ipix` funcid is chosen per overload (the real,real public overload emits
  the real,real ang2ipix), resolved by name in the same namespace as `req->funcid`
  (never via search_path); `funcformat = COERCE_EXPLICIT_CALL` to satisfy `equal()`
  against the stored index expression.
- Bound operators are the catalog int8 btree operators, whose `scalarineqsel` reads the
  expression index's histogram. The ranges are disjoint, so the planner's iterative OR
  combination `s1 + s2 − s1·s2` is essentially the exact sum.
- The BitmapOr path arises through the ordinary `generate_bitmap_or_paths` machinery —
  same executor shape as today, minus ~96 dead index scans.
- `q3c_dist_ok` is a new named recheck function (≡ `q3c_sindist < sin²(r/2)`) rather
  than a raw OpExpr precisely so it can carry its own selectivity (§4.4).
- Non-Const but *pseudoconstant* centers (Params from generic prepared plans, stable
  expressions) must not regress: they take the K-arm dynamic shape of §4.3. Only
  same-row/volatile centers fall through to the bare C predicate.
- `req->root` may be NULL (expression_planner contexts: index predicates, constraints)
  — handled.

### 4.3 Join path

`q3c_join(a.ra, a.dec, b.ra, b.dec, r)` cannot use `SupportRequestIndexCondition`
directly: its arguments are bare `ra`/`dec` Vars, and the index column is the
*expression* `q3c_ang2ipix(ra,dec)` — `match_funcclause_to_indexcol` requires a direct
argument `equal()` to the index expression, so it can never fire. Evaluated
alternatives:

- *Custom btree opclass* (`ipix <@ cone`): impossible — btree strategies are ordering
  comparisons. GiST/SP-GiST on (ra,dec) abandons the "existing btree keeps working"
  constraint (pgsphere's territory; possibly a separate experiment someday).
- *Single covering super-range via IndexCondition*: the ANDed-list restriction means
  one wrapper function could only emit one `[min_lo, max_hi]` range; the 4 nearby
  squares can be far apart in ipix space (quadrant/face boundaries), so this
  degenerates toward whole-face scans. Rejected.
- *Keep SQL inlining for joins, fix only selectivity*: the per-arm selectivity of
  non-Const-bound ranges stays pinned at the 0.005 default with no hook to fix it, the
  dummy operator must stay, and PARALLEL UNSAFE stays. Rejected.

**Recommended shape.** Simplify rewrites the call into an OR of per-arm wrapper
functions plus the recheck:

```
(   q3c_pix_circle(q3c_ang2ipix(b.ra,b.dec), a.ra, a.dec, r, 0)
 OR q3c_pix_circle(q3c_ang2ipix(b.ra,b.dec), a.ra, a.dec, r, 1)
 OR q3c_pix_circle(q3c_ang2ipix(b.ra,b.dec), a.ra, a.dec, r, 2)
 OR q3c_pix_circle(q3c_ang2ipix(b.ra,b.dec), a.ra, a.dec, r, 3)
) AND q3c_dist_ok(a.ra, a.dec, b.ra, b.dec, r)
```

`q3c_pix_circle(ipix, cra, cdec, rad, arm)` is a new C function (IMMUTABLE, PARALLEL
SAFE): runtime semantics "ipix lies in the arm-th nearby range of the cone". Its
SUPPORT function answers:

- **`SupportRequestIndexCondition`** — its argument 0 *is* the ang2ipix expression, so
  matching fires; it returns the two parameterized bounds
  `indexkey >= q3c_nearby_lo(a.ra, a.dec, r, arm)` and `<= q3c_nearby_hi(...)`
  with `lossy = false` (the bounds are exactly the function's semantics). Executor
  shape: Nested Loop → Bitmap Heap Scan → BitmapOr of 4 parameterized Bitmap Index
  Scans — precisely today's proven shape, now with a selectivity hook on every clause
  and full parallel safety. The bound-generating functions are stateless engine calls
  (per-row `q3c_region_set_center` + budget-12 cover), replacing the static-cache
  `q3c_nearby_it` trick.
- **`SupportRequestSelectivity`** — §4.4.

`q3c_ellipse_join` and `q3c_join_pm` get `q3c_pix_ellipse` / `q3c_pix_circle_pm`
analogues. The same K-arm shape serves pseudoconstant single-table centers (§4.2).

**Spike required first** (risk #1): support-based IndexCondition matching *inside OR
arms* goes through `generate_bitmap_or_paths → build_paths_for_OR → match_clause_to_
indexcol`, i.e. the generic machinery, but PostGIS never exercises this path — verify
on PG 14 and 17 before committing to the shape. **Plan B** (documented, viable):
Simplify emits raw OpExpr range pairs (today's tree shape, but built in C — still
adaptive per-arm, still PARALLEL SAFE) and the arm selectivity correction moves into
`q3c_dist_ok`'s estimate.

**Argument-order insensitivity** (later phase, UX win): at Simplify time the base-rel
arrays aren't built yet, but each side's Var → RTE → relation OID →
`RelationGetIndexList` + expression comparison identifies which side has a q3c index;
if only the *first* coordinate pair's relation has one, emit the mirrored rewrite.
One side only, deterministically — never both (their estimates would multiply and
square the selectivity).

### 4.4 Selectivity

**Restriction (constant center).** The planner's histogram estimate of the emitted
Const ranges is already good; the fix needed is the recheck clause. `q3c_dist_ok`'s
SUPPORT answers `SupportRequestSelectivity` with the **conditional** ratio

```
sel(recheck | ranges) = Ω_region / Ω_covered_ranges
```

using `q3c_ranges_solid_angle` on the same range list (cheap; cached per RestrictInfo
by the planner). The product — histogram density over the covered ranges × geometric
fraction of the covered area actually inside the region — is exactly the right
conditioning under local uniformity, and replaces today's flat 0.3333 factor. All
`estimate_expression_value` results are `IsA(..., Const)`-checked (fixing the 2.x
crash).

**Join.** `q3c_pix_circle`'s SUPPORT, in join context (`sjinfo != NULL`), computes the
expected match fraction from **both sides' statistics**:

1. Radius: `estimate_expression_value(args[3])`; Const → use it; Var → use its own
   column statistics (median) — radius-as-column becomes a *supported estimated* case
   instead of a crash; else a clamped default.
2. Inner side: `examine_variable` on `args[0]` (the ang2ipix expression) →
   expression-index histogram (int8 bounds h_0..h_n).
3. Outer side: construct the `q3c_ang2ipix(args[1], args[2])` FuncExpr and
   `examine_variable` it — hits the *outer* table's q3c expression-index statistics.
4. Cone measure in ipix units: `A = Ω_cone / Ω_avg_pixel` (face-position-corrected via
   the engine in a later iteration; the cube projection's pixel-area variation is a
   bounded few-tens-of-percent systematic).
5. Two-pointer walk over both histograms (O(n+m)):
   `F = Σ overlap_fraction · density_outer · density_inner · A`
   — i.e. ∫ outer-density × inner-density × cone-footprint, valid because a small
   cone's ipix footprint is local. Multiply by (1−nullfrac) factors; clamp; return
   F/4 per arm (the OR recombines to ≈F).
6. Fallbacks, in order: missing histograms degrade stepwise until the last resort is
   the uniform-sky `Ω_cone/4π` — today's formula, correctly demoted from the only
   answer to the final fallback.

`q3c_dist_ok`'s join-context selectivity returns the cone/nearby-union area ratio (the
candidate→exact correction, ≈0.3–0.6, tuned empirically).

This deletes `==<<>>==`, `q3c_seloper`, `q3c_sel`, `q3c_seljoin`, and type `q3c_type`
outright — and with them the q3c_join_pm `$10`/`$11` bug and the IsA-less Const casts.

**Statistics quality.** Document (and optionally ship a helper
`q3c_prepare_index(regclass)` that emits)
`ALTER INDEX ... ALTER COLUMN 1 SET STATISTICS 3000..10000; ANALYZE;` — expression-index
statistics targets are the single cheapest accuracy multiplier for clustered sky data.

### 4.5 Plan stability

The flip-proneness is attacked from both sides at once: rows (statistics-based
estimates on both restriction and join paths) and cost (only real ranges are planned;
Const bounds cost honestly; recheck functions get truthful `procost`). Remaining
measures: smooth N(radius) from the engine (§3.6), and the README's
`enable_seqscan = off` era ends — replaced by the statistics-target guidance plus a
pointer at `pg_hint_plan` as the escape hatch for pathological cases.

## 5. Compatibility and migration

- Upgrade script `q3c--2.0.5--3.0.0.sql`: `CREATE OR REPLACE` for every public
  predicate (SQL→C with identical signatures is legal and **preserves OIDs** —
  in particular `q3c_ang2ipix` is never dropped, since index expressions reference its
  OID). New objects: `q3c_pix_circle` / `q3c_pix_ellipse` / `q3c_pix_circle_pm`,
  `q3c_dist_ok`, `q3c_ell_ok`, the support function(s). Drops: the `==<<>>==` operator,
  `q3c_seloper`, `q3c_sel`, `q3c_seljoin`, type `q3c_type`.
- **Existing indexes: zero action.** Same expression, same funcid, same opclass. The
  upgrade is `ALTER EXTENSION q3c UPDATE;` + one `ANALYZE`. Views/matviews store the
  un-inlined `q3c_join(...)` call and therefore survive and immediately benefit.
- Legacy `*_it` functions remain as thin compatibility shims over the new engine
  (compute once with budget 100, expose the old fixed-array view; the static caches
  are confined to the shims); user SQL written against them keeps working, deprecation
  later.
- Version gating: `#if PG_VERSION_NUM < 140000 #error "q3c 3.x requires PostgreSQL 14+;
  use the 2.0.x branch"`; the 2.0.x branch stays alive for older servers.
- Behaviour deltas to document: EXPLAIN plan shapes change; parallel plans appear;
  ellipse membership changes near boundaries (focal definition); cones >35°, polygons
  >23°, and >100-vertex polygons now work; self-intersecting polygons get defined
  odd-even semantics; q3c_join argument-order sensitivity disappears in the phase that
  ships side auto-detection (until then the 2.x convention is documented unchanged).

## 6. Risks and required prototypes, ordered

1. **Support-IndexCondition inside OR arms** (§4.3) — the join design leans on it;
   spike on PG 14 and 17 first. Plan B documented.
2. **`equal()` matching of the emitted ang2ipix tree** against stored index
   expressions across versions — in particular PG 16+ `varnullingrels` when `q3c_join`
   appears in `LEFT JOIN ... ON`; may need nulling-rel-aware copying of the coordinate
   Vars. Regression tests for outer-join usage.
3. **Generic prepared plans**: verify the K-arm shape is emitted and indexed under
   `plan_cache_mode = force_generic_plan`.
4. **Selectivity accuracy**: build a harness comparing EXPLAIN estimates vs actual
   rows across a grid of radii × sky-density patterns (uniform, clustered, disjoint
   footprints); target within ~2x everywhere. Becomes a permanent CI asset.
5. **ε calibration** (engine vector math vs haversine recheck): heavy fuzzing at the
   boundary (points at distance r ± 10^k·ulp), across -O2/FMA/x86-64/aarch64. The
   failure mode — lost boundary rows — is exactly the issue-#49 class.
6. **Ellipse predicate delta**: quantify old-vs-new membership disagreement as a
   function of size and axis ratio before release notes are written.
7. **Face-frame table** (§3.1) is derived by hand from `q3c_ang2ipix_xy`; the
   round-trip unit test is the first thing to write.
8. **Per-row join cost**: budget-12 cover target <5 µs/row; if the heap shows up in
   profiles, a specialized non-heap descent for `max_ranges ≤ 16`.

## 7. Testing strategy

1. **Frame/unit tests** (standalone build): round-trip `(ra,dec) → v → face coords →
   ipix` ≡ `q3c_ang2ipix` for 10⁷ points including poles, wraparound, face
   edges/corners; corner-vector determinism across neighbours.
2. **Property-based oracle** (main correctness harness): ~10⁴ random regions (caps with
   r log-uniform in [1e-8°, 180°]; ellipses a ∈ [1e-6°, 89°], b/a ∈ [1e-3, 1];
   polygons: convex, star-shaped, self-intersecting, n ∈ [3, 10⁴]) × budgets
   {8, 50, 256, 4096}; ~10⁴ points per region biased toward the boundary. Assert:
   `M(p)` ⇒ ipix(p) ∈ fulls ∪ partials (no lost rows — the hard invariant);
   ipix(p) ∈ fulls ⇒ `M(p)` when `cover_certain`; over-coverage monotone in budget,
   regression-tracked.
3. **Differential vs the 2.x engine** for small regions: identical row sets through
   (ranges + recheck); range lists themselves are expected to differ.
4. **SQL regression**: existing `sql/` suites pass unchanged (they compare rows, not
   plans); new cases: near-35° stress (34.9–35.1°, centers on face edges/corners —
   the #49 cases), r ∈ {89°, 90°, 91°, 179.9°, 180°}, whole sky, r = 0,
   sub-milliarcsecond cones, polygons spanning 3+ faces and enclosing a pole,
   5000-vertex polygon, bowtie polygon; EXPLAIN-shape tests and the estimate-accuracy
   harness (risk #4) wired into the PG 14–19 CI matrix.
5. **Performance gates**: plan-time cover (budget 256) <100 µs for r ∈ {1", 1°, 30°,
   100°}; join mode (budget 12) <5 µs/call; end-to-end `q3c_join` throughput vs 2.0.5
   on the existing join tests.

## 8. Phasing

- **Phase 0 — spikes**: OR-arm IndexCondition matching; emitted-tree `equal()`
  matching (incl. PG 16 nullingrels, generic-plan Params); face-frame round-trip.
  Go/no-go between the recommended join shape and Plan B.
- **Phase 1 — engine**: `q3c_vec.c` / `q3c_region.c` / `q3c_cover.c` + the oracle
  harness; `*_it` shims keep all existing SQL passing; all limits already gone at this
  layer.
- **Phase 2 — constant-center path**: C predicates + Simplify → Const ranges +
  `q3c_dist_ok` ratio selectivity; cone first, then ellipse/polygon.
- **Phase 3 — join path**: `q3c_pix_*` + IndexCondition + histogram join selectivity;
  drop the dummy operator; PARALLEL SAFE flip after the worker-safety audit.
- **Phase 4 — parity and release**: pm variant, Param shapes, argument-order
  auto-detection, `q3c_prepare_index`, upgrade script, README rewrite, accuracy
  harness in CI, 3.0.0 release + 2.0.x LTS statement.
